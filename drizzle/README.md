# Database migrations

`0001_meta_webhook_inbox.sql` creates the durable WhatsApp webhook inbox, urgent opt-outs and sender holds, test-send history, and transactional service-role RPCs. Apply it to the Supabase PostgreSQL project before registering the Meta webhook or sending a test message. This repository does not apply migrations automatically.

`0002_contacts.sql` adds imported contacts, consent evidence and review, suppressions, and the service-role eligibility function. `0003_campaigns.sql` adds frozen campaign audiences, state transitions, durable send attempts, sender rate slots, counts, audit, and webhook status projection. Apply them in numeric order. No migration is applied automatically.

`0004_contact_import_pgcrypto_path.sql` repairs existing installations of the contact import function. Supabase commonly stores `pgcrypto.digest` in the `extensions` schema; the original function search path omitted that schema, so the import failed with SQLSTATE `42883` before saving any rows. Run this migration once in the same Supabase project's SQL Editor after `0002_contacts.sql`, then retry the upload. It is safe to rerun. Fresh installations using the current `0002_contacts.sql` already include the repair; `0004` remains safe to apply in sequence.

The campaign worker is a separate long-running process started with `npm run worker` after installing dependencies. The command compiles only its server-side TypeScript entry with the installed TypeScript compiler, then runs the compiled process. It loads `.env.local` and `.env` when present, while preserving environment variables injected by the host. Creating a draft or scheduling through the dashboard never starts a send. The worker refuses to claim messages unless `WHATSAPP_SENDS_ENABLED=true`, all Meta settings and webhook subscription are verified, and these explicit send-window settings are present: `WHATSAPP_SEND_TIME_ZONE` (IANA name), `WHATSAPP_SEND_WINDOW_START` and `WHATSAPP_SEND_WINDOW_END` (`HH:MM`), and `WHATSAPP_SEND_DAYS` (comma-separated weekday numbers, Sunday `0`). Optional `WHATSAPP_WORKER_BATCH_SIZE` (default `5`) and `WHATSAPP_MIN_INTERVAL_MS` (default `1000`) set conservative bounds. A failure after a possible Meta POST is parked for manual reconciliation, never retried automatically. Do not turn sending on until the business has confirmed its consent evidence, allowed hours, and campaign content.

The migration keeps dedupe hashes and suppression evidence independently of raw webhook bodies. After the business approves a retention period, run `select public.redact_meta_webhook_payloads(<UTC cutoff>);` on a schedule with a service-role connection. This clears old envelope bodies and item bodies that no longer require review, while retaining unresolved inbound review material and status columns needed for reconciliation. Decide the cutoff and a hold-release review process before production sending.

Ambiguous inbound opt-out language creates a sender-wide hold and one `meta_ambiguous_opt_out_events` row per message. A definite STOP creates a `meta_confirmed_opt_out_events` row and a recipient-specific `meta_opt_outs` suppression when Meta supplies a usable identity. Workspace admins review each source at `/dashboard/meta/review`; every review requires a written reason in `meta_sender_hold_reviews`. The confirmed reconciliation RPC verifies the exact source message, matching recipient phone, and stored suppression. The release RPCs serialize reviews with new inbound events, clear each reviewed item's flag for later retention redaction, and release the sender hold only after every confirmed and ambiguous event is reviewed. Confirmed `meta_opt_outs` remain in force for their recipients. Missing or unusable provider identities remain held for manual resolution.

`0006_inbox.sql` adds the WhatsApp inbox: `inbox_conversations` and `inbox_messages`, triggers on `meta_webhook_items` that project inbound messages and delivery statuses, and the service-role RPCs `begin_inbox_reply` and `record_inbox_reply_result`. Apply it after `0001`; it is safe to rerun and backfills messages already in the webhook inbox when the inbox tables are empty. Inbox projection errors are logged as warnings and never fail webhook receipt. Message text is stored in `inbox_messages` independently of `redact_meta_webhook_payloads`, so decide a retention period for it as well before production use.

`0007_import_opt_in_attestation.sql` adds `attest_contacts_opt_in`, called by the contact import commit route when an administrator ticks the opt-in confirmation. It records a verified consent grant through `record_contact_consent` for each imported number, naming the administrator and the import batch. It skips any number with an active suppression, a revoke, or a stored WhatsApp STOP, so it can never override an opt-out. Apply it after `0002_contacts.sql`; it is safe to rerun and idempotent per batch and contact. `tests/unit/import-attestation-check.sql` verifies it on an empty scratch database.

`attest_contacts_opt_in` takes a mode: `confirmed` (the administrator ticked the box) or `auto` (`CONTACT_IMPORT_AUTO_ENABLE=true`, internal-list mode). Both record a verified grant and both skip opted-out numbers; the `auto` record states honestly that individual opt-in was not separately verified. Re-running 0007 drops and recreates the function with the mode parameter.

- `0008_send_to_any_saved_number.sql`: any saved number can receive campaigns (no consent-event or sender-hold check; STOP replies and active suppressions are still skipped). Adds `contact_batch_members` so "Selected import" audiences work. Apply after 0007. Check: `tests/unit/send-any-number-check.sql`.
